# 场景切换交接：CNN 直接权重 vs FxLMS 自适应（结论）

> 日期：2026-08-17 ｜ 状态：已修复（30% 交接）+ 待验证（continuous 模式）
> 关联：变更记录 [[变更记录_CHANGELOG.md]] 2026-08-17 条目 ｜ 分支 `scenezone-anc`

**一句话结论**：RESET 交接「信 CNN 不信 FxLMS」的设计，在当前步长（1e-6）下已经不成立——FxLMS 自己 1 秒就能收敛到新场景，CNN 那份权重反而成了累赘。30% 起步只是"减震"，根治方向是关掉 RESET（continuous）。

---

## 1. 问题现象（250→500→250 实测）

单独播 250Hz / 500Hz 各自降噪都还行，但播 250→500→250 序列时**方向不对称**：

- 250→500 切换后 500Hz 对消差（err 0.037~0.053）
- 500→250 切换后 250Hz 仍深对消（err 0.023）

## 2. 根因：交接机制，不是 30% 也不是"CNN 不准"

精确的说法是三层：

1. **CNN 不是"不准"，是"不如 FxLMS 对当前信号拟合得准"**。CNN 是训练集上的平均预测（几万样本的"一般规律"），FxLMS 是对当前这只喇叭、这个频率的**实时拟合**——给它时间，永远比 CNN 准。
2. **问题出在交接动作**：RESET 把「CNN 那份不够准的权重」塞回去，**覆盖**了「FxLMS 已经自适应好的那份更准的权重」。250Hz 方向 CNN 误差小、覆盖了也不痛；500Hz 方向 CNN 相位偏、覆盖了就倒退。
3. **30%（wc_cold_start）是"减震"不是"治病"**：它把 CNN 塞回去的破坏力从 100% 减到 30%，但**还是在塞回去**。

## 3. 修复与实测数据

修复：`apply_reset` 在 crossfade 前对 `wc_cur` 乘 `wc_cold_start`（默认 0.3），与 INIT 首帧一致。

| 指标 | 修复前（满幅交接） | 修复后（30% 交接） | 500Hz 单独基准 |
|---|---|---|---|
| 500Hz 段 err | 0.037 ~ 0.053 | **0.025 ~ 0.031** | 0.024 |
| 500Hz 段 anti | 0.19~0.21（偏大） | 0.12 起步→0.20 | 0.14~0.16 |
| 500→250 段 250Hz err | 0.023 | 0.017~0.021 | 0.022 |

30% 交接把 250→500 从"很差"拉到"接近 500Hz 单独水平"，且没有劣化原本就好的 500→250。

## 4. 关键发现：RESET 其实在"帮倒忙"

日志里最扎眼的一段（250→500，步长 1e-6，OCG hold=3 让 RESET 延迟了 ~3s）：

```
cb=3837  err=0.0242  ← FxLMS 自己已爬到 500Hz（RESET 还没触发！）
cb=4218  err=0.0272
cb=4601  err=0.0251
-> RESET (cb 4980)
cb=4980  err=0.0348  ← RESET 反而 spike 上去
cb=5360  err=0.0267
...
cb=6833  err=0.0306  ← 最后停在 0.028~0.031
```

**步长 1e-6 下，FxLMS 自己（不靠任何 RESET）3 秒内就把 500Hz 收敛到 err 0.024；RESET 一触发，从 30% 重起，反而 spike 到 0.035，最后停在 0.028~0.031——比 RESET 前的 0.024 还差一点。**

结论：步长从 4.89e-8 修大到 2.1e-7（默认）/ 1e-6（GFANC_STEP）后，FxLMS 自己爬得动，RESET 交接整个可能都不需要了。之前 RESET 是为了救「小步长硬爬 2~3s」，这个前提已经消失。

## 5. 收敛时间澄清（vs 商业降噪耳机）

「3 秒才收敛」是错觉，三个时间要分开：

| 环节 | 耗时 | 是什么 |
|---|---|---|
| FxLMS 真正收敛 | **~1 秒** | 日志里 500Hz err 0.027→0.024 约 1 个诊断间隔 |
| OCG hold=3 | ~3 秒 | **故意的防抖延迟**（候选簇连续 3 帧才切），现模型已稳、属多余 |
| CNN 窗口 | ~1 秒 | CNN 要看满 1 秒新噪声才能预测 |

**商业降噪耳机"感觉不到过程"是因为它根本没有"过程"**：用的是固定滤波器（出厂前对标定好的声学路径预调好），戴上即生效，不存在"收敛"；少数型号的自适应只是几秒~几分钟的慢漂移补偿，主力对消是固定的。

本系统是**场景自适应**（CNN 认噪声 1s → 猜滤波器 → FxLMS 微调 1s），这个 ~1 秒是"自适应 + 切场景"的固有代价——它在从 250Hz 完全换到 500Hz 这样的不同场景，固定滤波器做不到这一点。**这是两条技术路线，不是 bug。**

## 6. 下一步（待验证）

A. **关掉 RESET 走 continuous**（最彻底，砍掉"信 CNN"这一步）：
```powershell
$env:GFANC_STEP='1e-6'
$env:GFANC_MODE='continuous'
.\scenezone_realtime.exe
```
预期：250→500 全程靠 FxLMS 自己爬，~1 秒到位、无 spike。若 250→500→250 都稳，则「CNN 直接权重 + 切场景」可简化为「首帧 CNN 起跳 + FxLMS 永续自适应」。

B. 只把 OCG 防抖砍到 1（保留切换、去 3 秒拖沓）：`$env:GFANC_OCG_HOLD='1'`

## 附：OCG 本次实测表现（正常）

两次 RESET 都是「真切换 + 簇复用」，**没有反复翻转**（P0-3 失败态未出现）：

- 250→500：`RESET (OCG clu=1/2)` → 新建簇 1，稳定 cos≈0.98~1.00
- 500→250：`RESET (OCG clu=0/2)` → **复用簇 0**，稳定

说明当前模型撑得起 OCG（至少 250↔500 两个纯音场景）。OCG 与交接修复是两层：OCG 管「何时切」，apply_reset 管「怎么交班」，互不影响。
